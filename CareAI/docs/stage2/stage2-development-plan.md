# CareAI Stage 2：终生健康 Memory 与主动健康管理开发计划

## 1. 阶段目标

第一阶段已实现：健康数据录入、可追溯的本地风险规则、AI 解释和 7 天计划、SQLite 历史记录、两次报告对比与基础趋势。

第二阶段要解决的产品问题是：现有功能仍以“用户提交一次数据后获得一次报告”为中心，不能充分体现长期健康记忆、主动发现与持续执行的价值。

**Stage 2 交付目标：**

```text
个人健康档案
    ↓
带日期和来源的健康记录／健康事件
    ↓
健康 Memory 时间轴与多次趋势分析
    ↓
基于个人历史的非诊断性趋势提醒
    ↓
个人化计划、完成记录、每周复盘
    ↓
可导出给医生查看的健康摘要
```

## 2. 本阶段必须完成（P0）

### P0-1 个人健康档案与数据隔离

**要做**

- 建立用户档案：昵称、出生年份／年龄、性别、健康目标，以及可选的既往情况、长期用药和过敏信息。
- 为报告、健康记录和计划增加 `user_id`，使各用户数据隔离。
- 为每条记录保存日期、录入时间、数据来源（手动录入／报告提取／模拟设备）。
- 提供删除个人健康记录的演示功能。

**验收标准**

- 用户 A 无法在历史页读取用户 B 的记录。
- 同一用户的记录可以按实际记录日期排序。
- 删除一条记录后，时间轴和趋势计算同步更新。

### P0-2 健康 Memory 时间轴

**要做**

- 以时间轴统一显示：健康指标、AI 报告、风险变化、行动计划和完成情况。
- 支持至少 BMI、血压、空腹血糖、睡眠、运动五类长期记录；没有数据时明确显示“资料不足”。
- 允许用户补录过去的健康检查数据；不得把未输入的数据推断为事实。

**验收标准**

- 使用一组至少跨 6 个月的模拟数据，可显示连续健康事件。
- 点击任一事件可查看输入数据、规则结果和对应建议。
- 时间轴不会将不同用户或不同日期的数据混合。

### P0-3 多点趋势与主动提醒

**要做**

- 从“仅和上一次对比”升级为最近 7 天、30 天、6 个月／全部记录的多点趋势。
- 增加个人基线概念：优先与该用户的历史范围比较，而非只套用通用阈值。
- 在新记录提交或打开健康主页时，生成非诊断性趋势提醒，例如连续睡眠下降、血压记录持续高于个人近期基线、体重持续上升、计划完成率持续偏低。
- 每条提醒显示：观察到的变化、比较区间、资料数量、风险提醒级别和建议的下一步。

**验收标准**

- 同一组固定模拟数据可稳定产生预期提醒；趋势规则有自动化测试。
- 少于设定最低数据点时，只显示“尚不足以判断趋势”，不制造预警。
- 趋势提醒不出现疾病诊断、处方或用药剂量。

### P0-4 长期行动计划、追踪与复盘

**要做**

- 将目前浏览器本地的 7 天打卡，改为后端按用户和计划保存。
- 用户可选择一个主要目标：睡眠、运动、体重管理或血压记录。
- 每周汇总计划完成率与相关指标变化；AI 基于已保存的历史与完成记录生成下一周建议。
- 用户可以标记计划未完成原因，供下次计划调整参考。

**验收标准**

- 刷新页面或更换浏览器会话后，已完成计划仍能读取。
- 系统能显示本周完成率、上周对比和下一周调整原因。
- AI 只能调整生活方式计划，不能给出处方、药物剂量或诊断结论。

## 3. 本阶段应完成（P1）

### P1-1 健康资料导入与结构化

- 支持 PDF／图片健康报告上传的演示入口，或以预置样例模拟报告导入。
- 提取并由用户确认日期、指标名称、数值、单位和来源后，才写入健康 Memory。
- 未确认、无法识别或单位不明确的值不得参与趋势计算。

### P1-2 医生健康摘要

- 生成可打印／下载的健康摘要：个人目标、近期趋势、异常提醒、用药自述、计划完成率和希望咨询的问题。
- 先定位为“辅助用户与医生沟通”，不宣称医生已审核、治疗或共同管理该用户。

### P1-3 产品定位与演示数据

- 首页文案调整为“终生健康 Memory 与主动健康管理”。
- 准备不含真实个人资料的 6–12 个月模拟数据，演示改善、恶化和资料不足三种情况。
- 更新演示脚本，突出“记住 → 发现 → 行动 → 复盘”的闭环。

## 4. 不在 Stage 2 承诺完成（长期路线）

以下能力保留为产品愿景或下一阶段工作，不能在本阶段演示时声称已接入：

- Apple Health、Google Fit、医院 HIS／EMR、诊所、药房或真实医疗设备的生产级接口。
- 医生账号、医生审核工作流和医生对 AI 计划的实时修改。
- 推送通知、短信、紧急联系人升级或急救分流。
- 使用真实患者健康资料开展测试。

这些能力需要外部合作、明确授权、隐私与安全设计、专业临床复核，以及相应的医疗责任安排。

## 5. 推荐开发顺序

| 顺序 | 任务 | 依赖 | 形成的可见价值 |
| ---: | --- | --- | --- |
| 1 | 数据模型迁移：用户、记录日期、来源、计划持久化 | 无 | 让“个人长期档案”成立 |
| 2 | 健康 Memory 时间轴 | 1 | 展示跨月份／年份资料 |
| 3 | 多点趋势规则与主动提醒 | 1、2 | 从被动问答升级为主动发现 |
| 4 | 计划追踪与每周复盘 | 1 | 从建议升级为执行闭环 |
| 5 | 医生健康摘要 | 2、3、4 | 体现 AI 辅助医患沟通 |
| 6 | 报告导入演示与界面重定位 | 1、2 | 完整体现最终产品愿景 |

## 6. Stage 2 完成定义

当以下条件均满足时，第二阶段可以称为完成：

- 可创建至少两个演示用户，且数据在页面和接口层面隔离。
- 一名用户拥有跨至少 6 个月的模拟健康 Memory 时间轴。
- 系统可基于至少 3 个历史数据点输出可解释的趋势提醒，或在资料不足时明确不作判断。
- 行动计划与完成记录保存在后端，并能产生一次每周复盘。
- 可导出一份明确标注“非诊断性、供沟通参考”的医生健康摘要。
- 新增核心逻辑有自动化测试；前端构建与后端测试均通过。
- Demo 始终不使用真实敏感健康资料，不作疾病诊断或医疗处方。
